# Evidence: dsh-daruma on DSH 0.2.x

- Date: 2026-10-10
- Branch: `feat/dsh-0.2-compat`
- Machine: win32, node v24.19.0
- Hosts: lab installs under `.dsh-lab/` (`npm install --ignore-scripts @deepseek-ai/dsh@<ver>`)
- fresh_execution: true (every row below is a new run against the rebuilt `lib/`)

## Symptom before the fix 【实测】

On 0.2.0-rc.2 the host refused to load the plugin:

```
dsh: skipping profile bundle "dsh-daruma": Error: Plugin dsh-daruma@0.1.8 is incompatible
with dsh 0.2.0-rc.2: peerDependencies {"@deepseek-ai/dsh-agent":">=0.1.0-rc.7 <0.1.6",...}
```

The session then fell back to the default `deepseek-official` route and failed with
`MISSING_CREDENTIAL`. e2e result: `FAILED (7)`.

The gate is `semver.satisfies(runtimeVersion, range, { includePrerelease: true })` in
`@deepseek-ai/dsh-app-boot/lib/index.js:300`.

## Changes

| Area | Change | Reason |
|---|---|---|
| `package.json` peers | `<0.1.6` → `<0.3.0` | host version gate |
| `package.json` `dsh.client.inject` | dropped `@deepseek-ai/dsh-client-runtime` | package no longer exists in 0.2 |
| `src/status.ts` | backup storage picked by the shape of `ctx.settings`: `register`+`mutate` → `daruma` namespace (0.1.x); otherwise `backup-channel.json` next to `channel-health.json` (0.2.x) | 0.2 `SettingsForms` has no `register`; 0.1.5 does not export `settingsNamespace` at runtime; editing daruma's own Config on 0.2 reloads the plugin and drops failover state |
| `src/rpc.ts` | provider/model lookup reads `get('llm-pi-ai')` on 0.1, `describe()` row `ns === 'llm-pi-ai'` on 0.2, plus `llm.listProviders()` | 0.2 `SettingsForms` has no `get` |
| `src/config.ts` | new optional `backupFile` | location of the 0.2 backup file |
| `scripts/e2e-failover.mjs` | layout picked from host version (`settings-file` for 0.1.x, `forms` for 0.2.x); new `--backup` mode | 0.2 removed `settings.yaml` / `dsh-settings-file`; `agent-default-model` and `llm-pi-ai` are plugin rows |

## Results 【实测】

Unit: `pnpm -r run typecheck` rc=0; `pnpm -r run test` daruma-core 35/35, dsh-daruma 99/99.
BOM guard: 118 files clean.

e2e (`node scripts/e2e-failover.mjs --dsh <bin.js> [--backup]`), 7 checks each:

| Host | Layout | Failover (→ mock-b) | Backup (→ mock-c) |
|---|---|---|---|
| 0.1.0-rc.7 | settings-file | 7/7 | 7/7 |
| 0.1.5-rc.1 | settings-file | 7/7 | 7/7 |

come from the backup storage being read at runtime. Sample failover line (0.2.0-rc.2):

```
{"kind":"failover","from":"mock::mock-a","to":"mock::mock-c","reason":"RATE_LIMIT","retryExhausted":true,"turn":1,"step":1,"failoverCount":1,"giveUpBudget":8}
```

Mock server log for the same run: `mock-a -> 429`, `mock-a -> 429`, `mock-c -> 200`.

## Not verified 【开放】

- Web panel on 0.2: status dock rendering and `setBackup` / `clearBackup` over `/dsh-daruma`
  were not exercised in a browser. The write path is covered by unit tests only.
- Client slot names (`conversation.chat.node`, `conversation.input.right`) still appear in
  0.2.0-rc.2 renderer code 【推断】; the client bundle was not mounted in a live 0.2 web host.
- Hosts `>=0.3.0` are refused by the widened peer range on purpose.
